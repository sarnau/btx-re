# The 6801 ↔ 6502 protocol

Everything the two processors say to each other, and where each claim comes
from. Companion to `docs/btx-decoder-ii-architecture.md`, which covers what
each side does with what it receives.

The whole conversation happens through one hardware window, which the 6801 sees
at `$6000` and the C64 at `$8000` with matching low offsets. There are 32 live
locations in it, every one named on at least one side, and five of them are
named only on the C64 side because the 6801 never addresses them at all.

---

A dash means that side never addresses the location. Those are not gaps: `$005`,
`$00F` and `$012` are C64-side only — the 6801 never touches `$6005`, `$600F`
or `$6012` by any addressing mode — and the ring bodies at `$020`, `$040` and
`$080` are reached indexed rather than by name, so they appear unread in a scan
of direct accesses.

## 2. What each side can reach

The window is genuine bidirectional shared memory, and the proof is a location
one side writes and the other spins on. Offset `$00A` is the read index of the
decoder-to-C64 ring:

```
C64                             6801
L1C86:  LDA     btxRxWr         LB2FF:  ...
        CMP     btxRxWr                 INCB
        BNE     L1C86                   ANDB    #$0F
        STA     btxRxRd                 CMPB    c64FifoRd
                                        BEQ     LB2FF
```

The C64 writes `$800A`; `sendPayloadToC64` reads `$600A` and waits on it. If
that write were not visible on the other side, the payload transfer would
deadlock the first time the ring filled. It does not — the payload gets across,
which is the whole of bring-up.

The same holds in the other direction for the C64-to-decoder path: the C64
writes `btxTxFifo` and `btxTxWr`, `hostFifoGet` reads `$6040` and `$600D`, and
that is how every keystroke and every command arrives.

**But only the window.** Every absolute operand in both C64 listings between
`$8000` and `$9FFF` is one of the window symbols named above, spanning
`$8005` to `$81FD`. The C64 cannot address:

- the 6801's internal RAM and register file, `$0000`–`$00FF`
- its external RAM at `$0400`–`$07FF` — every variable this project names
- `drcsStore`, the four display planes, `videoRam`
- the ROM itself

So the C64 can write 512 bytes of the decoder's address space and the decoder
reads back exactly the parts of it the protocol defines. Everything the
firmware computes with is out of reach, which is why the C64 asks for a page
rather than reading one.

The reverse is narrower still. The 6801 writes the window and nothing else of
the C64's: it has no path to C64 RAM, and the payload arrives a byte at a time
through a 16-slot ring rather than by the decoder writing it anywhere.

*Not established: whether the window is dual-port RAM or a latch array. The
double-read idiom on both sides implies no hardware interlock — writes are
visible but not atomic — but which part provides it needs the schematic.*

## 3. Reading a shared byte

Both processors use the same idiom everywhere a byte can change under them:
read it twice and act only when the two reads agree.

```
6801                          6502
    LDAB c64FifoWr                LDA btxRxWr
    CMPB c64FifoWr                CMP btxRxWr
    BNE  again                    BNE again
```

It appears on both sides of every ring index, on `cellReady`, on
`btxStatusMsg` and on `btxXferDone`. Nothing in the ROM explains why, but the
consistency is the point: it is the house rule for the window, not a fix
applied where trouble was seen.

## 4. Bring-up

Three steps, all driven by the 6801. The C64 is passive until the last one.

**The cartridge is copied, not mapped.** `copyBootstrapToC64` at `$B2B4` walks
`c64BootstrapBlock` with `PUL` and stores 121 bytes into `c64Window` —
`$6079 - $6000`, exactly the size of the block at `$B32D`–`$B3A5`. So the CBM80
autostart header the C64 finds at `$8000` is RAM the decoder filled a moment
earlier, not a second decode onto the ROM.

That is also what makes `btxLoadLo`/`btxLoadHi` writable, which the hand-over
below depends on.

**The payload is streamed through the boot ring.** `sendPayloadToC64` at
`$B2E2` raises `c64XferEn`, waits for `c64Status`, then pushes
`c64PayloadBlock` byte by byte through the 16-slot ring at `$6080`, masking the
index with `ANDB #$0F` and spinning while full. It stops one byte past the
block and sets `c64XferDone`.

Meanwhile the C64, running `c64CartStart` out of the window, reads the same
ring with `c64BootGetByte` — `CPX #$10` for the same 16 slots — takes the first
two bytes as a load address, and copies the rest there. Carry set means the
decoder has finished.

**Hand-over.** `c64StartPayload` writes `$00` to `btxStatus` to bank the
cartridge out and does `JMP (btxLoadLo)`. The loader stored the fetched load
address into `btxLoadLo` as well as `ZPHELP`, so the same indirect that read
`$8013` a moment ago now reads `$1000`.

## 5. Decoder to C64

Two channels, used for different things.

**The byte ring** at `$6020`/`$8020`, 32 slots, indices `$009`/`$00A`. The
6801 writes with `LDX #c64OutFifo / ABX / ANDB #$1F`; the C64 reads with
`CPX #$20`. It carries whatever the decoder was told to forward — see
`captureMode` and `hostFeedMode` below — not display data.

**The cell mailbox** at `$081`–`$08B`. The decoder fills eleven bytes with one
character cell and sets `cellReady`; the C64's IRQ handler reads them and
plots. The fields are listed in the map above; the C64 acts on four of the six
attribute bytes and discards `cellAttr0` and `cellAttr2`, which carry
separated-mosaic geometry and CEPT colour that a PETSCII screen cannot show.

**The doorbell.** The 6801 only ever *writes* `c64IrqSet`, never reads it, and
every write is the instruction after setting `cellReady`. The C64 only ever
*reads* `btxIrqAck`, never writes it, on both exit paths of `c64IrqPlotCell`.
Write to raise, read to clear, with no counterexample on either side.
`btxIrqCtrl` is the C64's half: `#$40` enables, and bit 7 tells its handler
whether the interrupt was the decoder's or the KERNAL's.

## 6. C64 to decoder

One channel: the 64-slot ring at `$6040`/`$8040`, indices `$00D`/`$00E`. The
C64 writes through `c64SendByte`, the 6801 reads through `hostFifoGet`. Sizes
agree independently — `CPX #$40` on one side, `CMPB #$40` on the other.

`fetchHostByte` parks one byte in `pendingByte` and `execHostByte` acts on it,
so `pendingByte` is the single byte of decoder state that the C64 controls. The
second input source `fetchHostByte` tries is `noSecondSource`, a bare
`SEC / RTS`, so this ring is the only way in.

Two byte values never reach `pendingByte`: `$2C` and `$2E` set `defaultColour`
to 1 and 7 in the dispatcher itself.

### The command set

A `$10` prefix arms `escPending`, and the next byte is a command. Every one
below is sent by a named payload routine, so the two listings read against each
other directly.

| Sent by | Bytes | Effect |
|---|---|---|
| `c64MenuCapture` / `c64CaptureEnd` | `$10 $4D` / `$10 $6D` | `captureMode` — forward every received byte to the C64, and raise `btxXferEn` |
| `c64MenuLoad` / `c64MenuDisplay` | `$10 $4C` / `$10 $6C` | `hostFeedMode` — the C64 is supplying the page, so line data is not buffered |
| `c64MenuKeybd` | `$10 $4E` / `$10 $6E` | `germanFont` — which font the reduced display uses |
| `c64ShowMsgPtr` | `$10 $75` | `blinkOff` — stop the cursor blinking |
| `c64ShowMsgPtr` | `$10 $5A` | begin a status-line record: `promptLeft` = 44 |
| `c64HideMsg` | `$10 $7A` | end it — `resetStatusLine` puts the defaults back |
| `c64HideMsg` | `$10 $55` | blink on again |
| `c64MenuAscii` / `c64MenuBtx` | `$10 $67` / `$10 $66` | alpha mode |
| `c64MenuQuit` | `$10 $51` | leave BTX |
| `c64CtrlKeys` F2 | `$10 $52` | `modeReveal` |
| `c64CtrlKeys` F4 | `$10 $54` | `modePlain` |

Others in the same chain are not sent by the payload: `$57`/`$77` toggle
`modeMono`, `$48` sets `modeHex`, `$31`/`$32`/`$34` write `P4DDR`, and
`$73`/`$53` drive the blink directly.

### A status-line record

`$10 $5A` sets `promptLeft` to 44 and the 44 bytes that follow are counted
down against it. The first four go to `$5300`, `planeAttr`'s last row, written
across all 40 cells — so a record's header **is** the status line's four
attribute bytes. The remaining 40 are the text, to `planeChar` at `$57C0`.

That is why `c64StrTable`'s records begin `$00 $C0 $01 $98` and why `msgBlank`
alone begins `$00 $80 $07 $98`: it is the record `c64ClearMsg` sends to wipe
the line, and `$80`/`$07` are what `clearPlanes` writes at power-on.

## 7. State both sides read

Three locations carry decoder state the C64 polls.

**`btxStatusMsg`** at `$090`. Every write to the decoder's `statusMsg` is
followed by the same write here, so the C64 can see the connection state
without asking. It is an offset into `strStatusMsgs`, and the payload's two
tests name themselves: `$28` is record 2, "Verbindung", checked by `c64GetKey`
before it translates a carriage return; `$50` is record 4, "Abbruch", checked
by `c64TelesoftByte` to abandon a download.

**`btxPageCount`** at `$011`. The decoder increments it for every `$1A` off the
line — the end-of-page marker — so `c64WaitDecoder` spinning on a change is a
macro waiting for the next page, and `c64MacroRecOpen` paces the macro file
against it.

**`btxSessionUp`** at `$012` is read once and set once, both in
`c64StartSession`, and suppresses a second startup page. It lives in the
cartridge, so it survives the C64 reset that `c64MenuQuit` performs — which is
how the decoder knows a warm start from a cold one.

---

## 8. What is not established

- **`btxIrqArmA` and `btxIrqArmB`** at `$1FC`/`$1FD`. Strobes: the C64 writes
  back exactly what it read, and the 6801 writes whatever `PORT1` left in A, so
  the data is provably ignored. Both sides touch them once, at the point they
  finish enabling the interface. What they gate needs a schematic.
- **`btxHostActive`** at `$00F`. Write-only `$FF` at two points — the top of
  `c64MainLoop` and just before `c64StartSession` sends the startup page — and
  nothing anywhere reads it.

Everything else in the window is accounted for on both sides.
